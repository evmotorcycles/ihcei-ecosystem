The cause — one line

govphys_quadratic_results.csv is line 7 of .gitignore.

The 992 per-repo rows were written to the runner’s disk, uploaded as a 59 KB artifact — and then discarded, because that exact filename could never enter the repository. The workflow run has since expired (now 404), so those rows are unrecoverable.

This is a packaging failure, not a scientific one. Nobody faked anything and nobody ran it wrong. Evidence was produced, then thrown away.

Does it weaken LISM? Narrowly, and honestly: the N = 992 cohort cannot be cited as offline-reproducible, so the linear-coupling claim rests on the two substrates that are committed. It does not mean the 992 result was wrong.

The same bug bit the yeast labels — and CI caught it

Identical failure mode, days earlier: scer_essential_orfs.txt sat on disk while listed in .gitignore. Every local run passed; a clean checkout had nothing. The first “gap closed” claim was false, CI failed it, and the audit’s original finding was correct. The labels are now genuinely committed and the gap is closed for real.

The root-cause fix, now in CI

test_no_ignored_evidence.py makes the class loud: any gitignored data file must be a declared gap carrying a reason and a remedy, and the yeast labels are asserted to be git-tracked (git ls-files --error-unmatch) rather than merely present on disk — exactly the check that catches a false closure on the spot.
